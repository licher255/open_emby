插件开发指南 — Plugin Architecture

设计参照 Dify 插件体系（manifest 驱动、权限声明、独立运行时、市场分发元数据） 与 VS Code 扩展模型（contributes 声明式贡献点、激活事件、扩展主机隔离）。 open_emby 的插件是"声明优先"的：manifest 说清自己是谁、要什么权限、贡献什么能力，宿主决定何时激活。

01插件类型

type用途入口 entry状态
workflowemby-engine 工作流包（风格化/重绘/生成，ComfyUI API 格式 JSON）workflow.json已支持
exporter新刺绣机格式导出器（PES/JEF/EXP…）TS 模块（sidecar 加载）下一迭代
tool编辑器工具（选区、配色、针法调整）JS 模块（渲染侧沙箱 iframe）下一迭代
agent-skill制版 Agent 能力（新工具/新策略）TS 模块 + 工具 schema后续
theme界面主题CSS / design tokens后续
model-pack模型包（emby-N-codename 谱系模型 + 推荐参数 + 示例）manifest 声明 + 模型文件后续

02Manifest（plugin.json）

{
  "id": "peony-style-pack",
  "name": "Peony Style Pack",
  "version": "0.1.0",
  "type": "workflow",
  "entry": "workflow.json",
  "description": "牡丹风格的色块化工作流",
  "author": "you",
  "license": "MIT",
  "minAppVersion": "0.0.1-beta",
  "permissions": ["engine"],
  "contributes": {
    "menus": [{ "id": "peony.apply", "label": "Apply Peony Style" }],
    "panels": []
  }
}
  • minAppVersion — 参照 Dify 的兼容性声明，宿主版本不满足则拒绝激活。
  • permissions — 声明式权限，宿主逐项授权（见下节）。
  • contributes — 参照 VS Code 的贡献点：菜单、面板、命令，宿主据此挂载 UI，不需要插件直接操作 DOM。

03权限模型

权限能力风险
engine向 emby-engine 提交/查询工作流低（本地计算）
sidecar调用制版核心 API（针迹生成/导出）低
fs限定数据根目录内读写中（越界路径一律拒绝）
net外网访问（下载模型等）高（安装时明示）
原则 — 默认零权限；每个权限在安装/启用时逐项向用户明示（Dify 市场同款交互）。

04生命周期

# 宿主（src/main/services/pluginHost.ts）
discover   # 扫描 plugins/ 与用户插件目录
validate   # manifest schema 校验 + 权限清单审查
install    # 登记到用户配置（默认停用）
activate   # 按 activationEvents 惰性激活（Dify 式：用到才加载）
deactivate # 释放资源；停用不卸载文件

05沙箱与隔离

  • 渲染侧插件（tool/theme）：隔离 iframe + 受限 postMessage API，无 DOM 直访。
  • 主进程/编排侧插件（exporter/agent-skill）：在 sidecar 内运行，权限逐项授权； 重计算必须走 emby-core/emby-engine 的既有接口，不允许插件自带二进制（安全审查边界）。
  • workflow 插件：纯 JSON，天然安全——只描述节点图，由引擎执行。

06分发与社区

  • 当前：plugins/<id>/ 目录 + PR 收录，CI 校验 manifest schema。
  • 规划：插件市场页（Dify Marketplace 式卡片流），model-pack 与 workflow 是首批上架类型； 模型包遵循 emby-N-codename 谱系命名（见模型谱系约定）。

07贡献流程

  • Fork 仓库，在 plugins/<your-id>/ 开发。
  • manifest 通过 plugins/plugin.schema.json 校验，pnpm run typecheck 通过。
  • PR 附：插件说明、截图、权限说明。
